## 2. Recommended architecture and approval point

**Use a fixed 303 to React and activate the session in a guarded same-origin POST.** This changes the requested issuance timing. The callback verifies Google identity and prepares a short-lived one-time handoff. The existing refresh route, in an explicit handoff mode, creates the ADR-003 session after React confirms the initiating tab still owns the attempt. Ordinary refresh continues to rotate existing sessions.

Writing `outpost_refresh` directly on the Google callback can overwrite a newer password/phone cookie or install a session after another tab signs out. React runs after that write. The current generation counter disappears across a full navigation, cross-tab notices are transient, and a Web Lock acquired by the initiating page does not span the redirect. A server epoch checked only at callback entry also misses a response already in flight. The guarded POST keeps the active cookie write inside the existing same-origin auth serialization. It adds one transient handoff record and one mode on an existing route. It requires no database schema change. [Web Locks specification](https://www.w3.org/TR/web-locks/)

If issuing the active refresh cookie in the callback remains mandatory, treat logout/account-switch precedence as an unresolved implementation blocker. That variant needs a separately approved server-side invalidation and cookie-write design before enablement. A completion-page guard alone cannot satisfy it.

## 3. Exact proposed backend and browser contracts

| Step | Proposed contract |
|---|---|
| Start | React obtains the existing `acadboost-session` Web Lock briefly, writes a new random public attempt ID with an expiry to same-origin `localStorage` and to its own `sessionStorage`, then navigates to `GET /api/v1/auth/google/authorize?attempt=<uuid>`. The attempt ID is a selector, grants no authority and travels only to the first-party authorize endpoint and the later POST header. No return URL parameter. Require valid UUID and configured Google feature. Keep the existing 302 Google redirect, M01A state/cookie and 600-second TTL. Extend the stored state with the selector. |
| Callback | Google returns to `GET /api/v1/auth/google/callback`. Keep M01A's cookie scope, digest check, atomic single use and matched-only cleanup. Return the selector from the same validated state operation. Keep Google endpoint, PKCE, nonce, issuer, audience, signature, expiry, verified email and stable-subject checks. On verified identity, write a 120-second Valkey handoff record and cookie. Return `303 Location: /auth/google/complete`. No active cookie write or token response. |
| Handoff credential | Use `__Secure-outpost_google_handoff` with a separate random 32-byte proof, Secure, HttpOnly, SameSite=Strict, host-only, `Path=/api/v1/auth/refresh`, `Max-Age=120`. Valkey key uses the proof digest and the record stores the validated identity projection, attempt selector and expiry. Never store provider code, Google tokens, verifier or raw handoff proof in that record. This proof is distinct from the M01A cookie and a standard refresh token. |
| Complete | The completion page calls `POST /api/v1/auth/refresh` under the existing Web Lock, with `X-Acadboost-Google-Attempt: <uuid>`, credentials included, same-origin Origin and no request body. Require feature enabled, exact configured Origin, valid selector and handoff cookie. Atomically consume the matching handoff once. A wrong selector, malformed, missing, expired or replayed handoff returns safe 401 without rotating an ordinary session or clearing someone else's handoff. |
| Session issuance | Before activation, reject an existing usable `outpost_refresh` with generic `409 session_conflict`. Use a read-only active-cookie lookup, with no rotation or replay side effect. Treat revoked/expired cookies as unusable and verify that behavior. This makes Google a signed-out sign-in flow. Use existing subject/collision rules and current account status at activation. Resolve identity and issue the session transactionally as today. Clear the matched handoff cookie, set the established Strict refresh cookie and return the existing bearer envelope. Keep the normal refresh branch unchanged for requests without the handoff header. |
| Authenticated UI | Load `GET /api/v1/me` with the returned bearer via the shared client. Publish the user and cookie account ID only after validating the still-current attempt and session generation. Clear the matching browser attempt, then replace-navigate to `dashboardPath(user.account_type)`. WorkspaceShell uses server-authorized organization membership and its existing empty state. |

Valkey handoff validation and consumption must happen before an identity or session write. Consume before the PostgreSQL transaction, so a PostgreSQL failure requires a fresh attempt and retry cannot issue twice. Validate the full handoff record before use. Keep bounded TTLs, scope keys separately and require `NX` on writes. Signing or transaction failure yields the existing safe error envelope at the POST. Continue using the common cookie serialization for the active session. Avoid a transitional callback JSON branch on enabled deployments that could bypass handoff coordination.

### Fixed failure behavior

Callback outcomes use only the fixed completion route and approved literal query values `?result=cancelled`, `?result=invalid` or `?result=unavailable`. The success route has no query. Treat these values as presentation hints only. Parse a cancellation only after a matching M01A proof and state have been consumed. Match the known Google `access_denied` outcome and clear the correlation cookie. Stale, missing and wrong-browser callbacks take the generic invalid outcome, retain any unmatched proof, and perform zero provider calls or writes. Configuration, Valkey and provider outages take unavailable. Unexpected callback errors use the safe server error path and log only fixed diagnostic categories and request IDs. Neither a failure redirect nor a user-edited result value triggers completion, clears a newer attempt or affects an existing session. Changing expected callback failures from API 401/503 JSON to fixed browser 303 outcomes is a proposed contract change requiring approval.

All auth handoff responses carry `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and the existing `X-Request-ID`. Keep `Pragma: no-cache` where already present. The provider's OAuth state and authorization code necessarily appear on the provider protocol URLs. Never copy them, provider errors, OAuth tokens, cookie proofs, identifiers or caller-controlled URLs into the application `Location`, UI, metrics or logs. Disable query and cookie capture at every proxy/APM layer serving the callback, including error/access logs. Keep request IDs in response headers and sanitized server logs, optionally storing the callback request ID in the transient handoff for a server-side join. The UI can show the safe request ID from a failed completion POST. Browser application navigation replaces the completion route after success. Treat history/referrer handling as browser tests and avoid claiming that React can erase the provider's browser history. [Google web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server)

## 4. Origin, cookies and provider prerequisites

- Use one canonical public HTTPS origin, for example `https://app.example.test`. The public ingress serves React, forwards `/api/*` unchanged to private Express and serves `index.html` for client routes including `/auth/google/complete`. Route `/api/*` before the SPA fallback. Pass Set-Cookie and root-relative Location unchanged. Restrict accepted host and trust forwarded headers only from the selected ingress. Suppress callback queries and auth cookies in telemetry. Use a dedicated trusted auth host with production and test cookies separated by hostname or browser profile. HTTPS ports share host-scoped cookies.
- Proposed backend settings are `OUTPOST_PUBLIC_APP_ORIGIN=https://<approved-host>`, `OUTPOST_GOOGLE_HANDOFF_ENABLED=false` by default, and `OUTPOST_GOOGLE_REDIRECT_URI=https://<approved-host>/api/v1/auth/google/callback`. In enabled mode validate an HTTPS origin with no userinfo/query/fragment or path, and require the redirect to equal origin plus the literal callback path. Server-held Google client ID/secret, auth signing key and Valkey are required. Compare completion `Origin` to the validated origin with no wildcard CORS. Keep frontend `VITE_API_BASE_URL=/api/v1` and propose `VITE_GOOGLE_SIGN_IN_ENABLED=false` by default. Frontend exposure depends on the matching backend and browser capabilities, and the backend feature gate applies even on direct API navigation.
- The M01A correlation cookie must reach Google's cross-site top-level GET callback, which is the reason for Lax. Do not expect the existing Strict refresh cookie on that request. Test that the cross-site top-level response sets the pending Strict cookie and that the later React-origin POST sends it. Then verify the established refresh cookie is delivered by the same-origin POST response and is used for a fresh page restore. Keep the existing Secure, HttpOnly, Strict and `/api/v1/auth` active cookie. [HTTP cookie processing rules](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis)
- For deterministic browser acceptance, terminate HTTPS at `https://localhost:<fixed-test-port>` and route Vite and Express through that same origin. Use a trusted test certificate, or isolate self-signed allowances to a disposable browser context. Use `localhost` end to end and use a fake provider on a distinct HTTPS site or intercept it. Test `127.0.0.1` as a mismatch. Do not weaken cookies for the current HTTP dev setup. Real Google acceptance uses a separately approved HTTPS host and the exact registered redirect, including scheme, hostname, port and path. Check provider OAuth web client, consent/test-user policy, secret management, working TLS and DNS, and intended deployment host before enablement. [Google redirect URI requirements](https://developers.google.com/identity/protocols/oauth2/web-server#creatingcred)

## 5. React and recovery behavior

`GoogleLoginPage.jsx` retains `AuthLayout` and `AuthMethodNav`. Show a single Continue with Google action only when enabled and prerequisites are supported. Disable it while the tab is preparing navigation and announce progress with `role=status`. Present the approved error with an accessible heading, focus and a retry action. Password and phone choices remain available. Avoid exposing duplicate or disabled navigation as a promised provider flow.

A new `GoogleCompletionPage.jsx` runs outside `WorkspaceShell` and delegates to `authApi.js` and the shared session client. Deduplicate concurrent React effects and completion visits by attempt, and prevent a stale page navigation after unmount or a newer intent. Handle these outcomes:

| Outcome | UI and retry |
|---|---|
| Verified and active | Load `/me`, publish through existing session store and replace into the correct dashboard. Reload restores the existing session normally. |
| Cancellation or expired/invalid/replayed proof | Show generic cancellation or expiration copy and offer a fresh Google start. Never retry the provider code or re-activate the old handoff. |
| Network error or provider/Valkey outage | Distinguish unavailable from denied. Offer fresh sign-in, or an explicit bounded retry only if the client can prove the request was never dispatched. Suppress automatic POST replay. |
| Activation or `/me` failure | Treat HTTP 401 as expired/revoked. Treat 409 as an existing session, with a way to resume that session or sign out explicitly. Treat an uncertain POST result as unconfirmed and never declare Google success from whichever refresh cookie happens to exist. Test the lost-response/cleanup case before release. |
| Missing, stale or already used tab intent | Skip activation. Offer restart or deliberate resume of an already confirmed app session. Reload/back of a completed route must never repeat the exchange. |
| Logout or account change | Show the current user intent, stop stale workspace navigation and keep the session dialog's existing uncertain-logout recovery path. |

Use the existing error/status conventions without globally changing `restoreAuthSession`'s null-return behavior. A handoff-specific operation should surface typed failures from POST and `/me` while sharing transport, lock and publication internals. Do not call `apiRequest` recursively under the lock if it can initiate another locked refresh.

## 6. Identity and collisions

A returning Google subject resolves its existing user and memberships. The current resolver creates a new `student` by schema default if the Google subject is new. It copies verified email only when the primary email is free. If a password account already holds it, current behavior creates a distinct Google user with no primary email and no inherited organizations. Keep that behavior during this slice unless product separately approves a reject-and-guide-to-password policy. The UI should say that the current sign-in may not have access and offer the established password method without announcing that a different account exists. Suspended accounts get the same generic denial. Authorized users without memberships reach the normal empty workspace or account path. Google never grants staff or tenant permissions. Proof-bound linking and unlinking are M01D.

## 7. Concurrency and logout/account-switch precedence

Use the existing origin-wide Web Lock and a durable non-credential intent, with an exact tab match from `sessionStorage`. Beginning a new explicit Google attempt supersedes the prior pending attempt. Explicit password/phone authentication and current/all logout invalidate any pending Google attempt at user intent time, including uncertain logout. They use the same cookie mutation lock. Maintain the existing logout guard on reload. A new Google attempt requires a new explicit gesture after any pending logout is resolved. If storage or Web Locks is unavailable, fail closed for Google and leave existing login methods usable. Storage and broadcast messages guide the app. Server proof, exact Origin, active-cookie exclusion and transactional activation remain independent checks.

| Race | Defined outcome and test |
|---|---|
| Double click or two starts in one tab | One navigation per accepted click. A newer accepted intent replaces the previous intent. Two authorize responses may still reach the browser out of order. Duplicated tabs can inherit a copy of sessionStorage. Test that two copies of the same intent still redeem once under the lock and Valkey consume. |
| Multiple tabs or an older callback | An older request can carry a proof that was valid when sent. It can complete provider verification or overwrite the single pending cookie if it was already in flight. The old tab's POST is barred by the shared intent. A newer tab sending the wrong pending proof gets an explicit restart. No active cookie change occurs in either callback. Verify response order in both directions. |
| Back/forward or repeated completion | Read durable intent again on restoration, including `pageshow` from back/forward cache. Old pages with no matching intent cannot POST. React coalesces duplicate work within a mount and Valkey denies retries after consume. |
| Logout or account switch before activation | Invalidate the shared intent synchronously and check it again inside the cookie lock immediately before POST. Callback has no active cookie effect. An existing valid session also blocks Google activation on the server. |
| Logout or account switch after activation dispatch | Serialize cookie mutations under the lock. Recheck the intent after the POST and before publishing. If superseded while a successful activation was in flight, revoke the exact newly issued session under the same lock using its returned bearer and the existing logout route, while its cookie is current. Publish no stale user. The newer action proceeds once cleanup finishes. Preserve separate account ownership in pending logout paths. Verify behavior with deferred responses and real browser cookie ownership. |
| Uncertain response, unload or crash | Keep handoff fetch non-keepalive. Block automatic handoff recovery and preserve an unresolved auth state if compensation cannot be confirmed. Do not blindly refresh or revoke an unrelated account. Browser tests must show that a lost response, abort or unloaded tab cannot leave an active stale Google session that another tab restores after logout or a switch. If a browser can install a stale cookie under these conditions, hold release and approve a server-side attempt/session receipt and targeted revocation design. A client flag alone is insufficient. |
| Remote revocation or suspension | `/me` and ordinary refresh must still enforce current session/account status. Recheck active user at issuance with existing transaction rules. Existing logout-all revokes current families. Invalidating pre-existing pending OAuth grants across devices would require an account-level policy and server fence, which is a separate approval question. |

The linearization point is the guarded handoff POST, within the serialized cookie operation. A cancellation seen before dispatch blocks the POST. After dispatch, compensation and the next locked mutation govern the outcome. The in-flight network test is a release gate and must validate server-side session usability as well as the visible UI.

## 10. Approval checklist

1. Approve the change in issuance timing. Callback validates Google and redirects with a one-time pending handoff. The guarded same-origin mode on the existing refresh route issues the active session.
2. Approve the fixed completion path and generic 303 failure outcomes, including the deliberate replacement of current callback JSON responses.
3. Approve the public HTTPS origin, exact callback URI, ingress ownership, localhost fixture and feature-flag rollout. Supply real credentials and register the redirect only in a separately authorized acceptance step.
4. Approve Google as a signed-out sign-in flow and the handling of an existing session conflict. Confirm browser capability gating, shared-tab precedence, compensation behavior and the stop condition if abort/crash testing exposes a stale usable session.
5. Ratify first-use Student creation, the matching-email separate-account behavior and generic password fallback. Approve any different collision or across-device pending-grant policy separately. Account linking remains M01D.
6. Approve the scoped file plan, test harness and real-provider acceptance criteria before implementation or enablement.

The deliverable is this specification. No implementation, database changes, provider configuration or Git commit are part of the planning task.
